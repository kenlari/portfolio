1. Executive summary

Vaultly is a small internal notes service. Testing found that its diagnostic endpoint is reachable without authentication and discloses the production API key and database password, that notes belonging to other users can be read by changing an identifier, and that the connectivity-check feature passes unsanitised input to a shell, allowing any unauthenticated visitor to run commands on the server.

The three issues chain: no credentials are required at any point. A single request yields the database password, and a second yields a shell as the application user. This represents full compromise of the host.

Business impact: complete loss of confidentiality of the notes database and of the credentials that protect it, plus remote code execution on the application server.

Recommendation: treat as an emergency. Disable /debug in production, enforce object-level authorization on /api/note, and replace the shell call in /ping with a non-shell network check. Rotate the exposed API key and database password immediately — they must be assumed compromised.

F1 — Unauthenticated information disclosure

/debug returns the live API key, database password and user list to anyone.

$ curl -s http://127.0.0.1:8080/debug
{
  "service": "vaultly",
  "version": "1.4.2",
  "api_key": "vault_live_9f2c41a7d8be4f0e9c6a1b3d5e7f8a90",
  "db_password": "Pr0d-Vaultly-2019!",
  "users": ["alice", "admin"]
}

Impact: instant credential compromise; the database password likely grants lateral movement beyond this host. Fix: remove the endpoint from the production build; if diagnostics are required, gate them behind admin auth and return health status only, never secrets. Rotate both credentials.

F2 — Broken object-level authorization (IDOR)

The endpoint takes an object id and returns it without checking that the caller owns it. There is no authentication at all, and even with auth the ownership check is missing.

$ for i in 1 2 3; do curl -s "http://127.0.0.1:8080/api/note?id=$i"; echo; done
{"id": 1, "owner": "alice", "body": "remember to rotate the staging key"}
{"id": 2, "owner": "admin", "body": "flag{idor_is_the_most_common_web_bug}"}
{"id": 3, "owner": "alice", "body": "lunch on friday?"}

Impact: read access to every other user's data; sequentially enumerable. Fix: authenticate the request, then authorize per object (note.owner_id == session.user_id) inside the data layer, not the UI.

F3 — OS command injection (critical)

host is interpolated into a shell string. Shell metacharacters execute.

$ curl -s "http://127.0.0.1:8080/ping?host=127.0.0.1%3Bid%3Buname%20-a"
uid=1000(kennethlari) gid=1000(kennethlari) groups=1000(kennethlari),...
Linux kali 7.1.5+kali-amd64 #1 SMP ... x86_64 GNU/Linux

Impact: remote code execution as the application user, unauthenticated. From here: read the app source, move to the database, persist. Fix: never use shell=True with user input. Use subprocess.run(["ping", "-c", "1", host], shell=False), validate host against a strict allowlist (or ipaddress.ip_address()), and drop the feature's privileges.

F4 — Banner disclosure (informational)

Server: Vaultly/1.4.2 lets an attacker map the build to known CVEs. Fix: suppress the version, or accept the risk.

4. Remediation priority

  1. Today — rotate the API key and database password; take /debug offline.
  2. This sprint — add authentication + object-level authorization to /api/note; remove shell=True from /ping.
  3. This quarter — add SAST/dependency scanning and a pre-production check that fails the build if debug routes are enabled.
